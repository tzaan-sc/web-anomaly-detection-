## TÓM TẮT ĐỒ ÁN (VIETNAMESE)

Trong kỷ nguyên số hóa, các hệ thống ứng dụng web lưu trữ và chia sẻ tệp tin trực tuyến ngày càng trở nên phổ biến và đóng vai trò quan trọng trong học tập, nghiên cứu và sản xuất kinh doanh. Tuy nhiên, sự gia tăng của các cuộc tấn công nhắm vào tầng ứng dụng (Application Layer Attacks) — đặc biệt là các hành vi **Lạm dụng logic nghiệp vụ (Business Logic Abuse)** và **Lỗ hổng kiểm soát truy cập cấp đối tượng (BOLA / IDOR)** — đang đặt ra thách thức an ninh mạng vô cùng nghiêm trọng. Khác với các cuộc tấn công cú pháp truyền thống (như SQL Injection, XSS), kẻ tấn công trong các kịch bản này sử dụng chính tài khoản hợp lệ để gửi các HTTP Request hoàn toàn đúng chuẩn cú pháp nhằm vét trộm dữ liệu (*Export Abuse*), xóa phá hoại tài nguyên (*Delete Abuse*) hoặc dò quét tài nguyên trái phép (*BOLA Scan*). Do đó, các hệ thống phòng thủ truyền thống như Tường lửa ứng dụng web (WAF) và Hệ thống phát hiện xâm nhập (IDS) dựa trên chữ ký gần như hoàn toàn bất lực.

Để giải quyết triệt để thách thức trên, đề tài đã nghiên cứu và xây dựng thành công hệ thống phát hiện hành vi bất thường khép kín tích hợp trên ứng dụng web lưu trữ tài liệu trực tuyến **StudyDrive** (phát triển bằng Flask 3.x, MySQL và Bootstrap 5). Hệ thống tích hợp cơ chế ghi nhật ký truy cập có cấu trúc (**Structured Request Logging**) tại tầng Middleware với 21 trường dữ liệu và mã hóa băm SHA-256 đối với Session ID nhằm đảm bảo tuyệt đối tính riêng tư. Dữ liệu truy cập được gom nhóm theo **cửa sổ trượt 5 phút** và trích xuất thành **vector 25 đặc trưng số** phản ánh lưu lượng, tần suất bùng nổ, tỷ lệ lỗi phân quyền và hành vi lạm dụng tệp.

Đề tài áp dụng thuật toán học máy không giám sát **Isolation Forest** với chiến lược huấn luyện **Normal-only Training** và phân chia tập dữ liệu theo nhóm (**Group-aware Split**) nhằm triệt tiêu hiện tượng rò rỉ dữ liệu (Data Leakage). Kết quả thực nghiệm trên tập Test độc lập cho thấy mô hình đạt độ chính xác **Accuracy 100%**, **Precision 100%**, **Recall 100%**, **F1-Score 1.000** và tỷ lệ báo động giả **FPR 0.0%**. Hệ thống tích hợp giao diện cảnh báo trực quan (**Alerts Dashboard**), khả năng truy vết log gốc (Forensic Log Investigation), cơ chế phòng thủ chủ động (**Active Defense**) tự động khóa tạm thời tài khoản vi phạm trong 60 phút và bộ kiểm thử tự động toàn diện gồm **44 bài test (100% Passed)**.

## ABSTRACT (ENGLISH)

In the era of digital transformation, web applications for online document storage and sharing have become fundamental infrastructure for education, research, and business operations. However, the surge in application-layer attacks—especially **Business Logic Abuse** and **Broken Object Level Authorization (BOLA/IDOR)**—presents severe cybersecurity challenges. Unlike conventional syntax-based attacks (e.g., SQL Injection, Cross-Site Scripting), adversaries in business logic attack scenarios utilize authenticated credentials to send syntactically valid HTTP requests to exfiltrate massive data (*Export Abuse*), maliciously destroy assets (*Delete Abuse*), or systematically enumerate unauthorized objects (*BOLA Scan*). Consequently, traditional perimeter defense mechanisms like signature-based Web Application Firewalls (WAF) and Intrusion Detection Systems (IDS) fail to detect these subtle threats.

To address these vulnerabilities, this project presents a comprehensive, end-to-end anomaly detection system seamlessly integrated into an online file management platform named **StudyDrive** (engineered using Flask 3.x, MySQL, and Bootstrap 5). The architecture incorporates an **Application-layer Structured Request Logging Middleware** that captures 21 contextual fields while safeguarding user privacy via SHA-256 session hashing. The sequential request logs are aggregated into **5-minute sliding time windows** and transformed into a quantitative **25-dimensional numerical feature vector** capturing traffic velocity, burstiness, authorization error rates, and file manipulation abuse.

The system deploys the unsupervised **Isolation Forest** algorithm trained under a **Normal-only Training** paradigm combined with a **Group-aware Split** strategy to rigorously eliminate data leakage. Empirical evaluation on an independent test set demonstrates optimal performance with **100% Accuracy**, **100% Precision**, **100% Recall**, **1.000 F1-Score**, and **0.0% False Positive Rate (FPR)** across all attack scenarios. Furthermore, the platform integrates an intuitive **Alerts Dashboard** with forensic log traceability, an **Active Defense** engine that automatically imposes a 60-minute provisional account freeze on anomalous entities, and an exhaustive automated test suite comprising **44 unit and integration test cases (100% Passed)**.

## MỞ ĐẦU

### 1. Đặt vấn đề
Trong bối cảnh bùng nổ của cuộc Cách mạng Công nghiệp lần thứ tư, các dịch vụ trực tuyến và ứng dụng web lưu trữ đám mây đã trở thành phương tiện thiết yếu phục vụ công tác quản lý tài liệu, trao đổi thông tin và chia sẻ tri thức. Đi cùng với sự tiện lợi đó, các nguy cơ tấn công an ninh mạng ở tầng ứng dụng (Application Layer) ngày càng diễn biến phức tạp và tinh vi.

Theo thống kê của tổ chức OWASP (Open Web Application Security Project), các cuộc tấn công khai thác lỗ hổng kiểm soát truy cập đối tượng (BOLA/IDOR) và lạm dụng logic nghiệp vụ (Business Logic Abuse) đang gia tăng mạnh mẽ và đứng đầu danh sách các rủi ro bảo mật nguy hiểm nhất. Những kẻ tấn công không sử dụng các chuỗi mã độc có cấu trúc bất thường (như SQL Injection hay XSS) mà tận dụng các phiên đăng nhập hợp lệ, gửi các HTTP Request đúng chuẩn ngữ pháp nhưng với tần suất, tốc độ hoặc trình tự bất thường để chiếm đoạt tài liệu nhạy cảm, xuất trộm dữ liệu quy mô lớn hoặc xóa sạch tài nguyên của người dùng khác. Trước các đòn tấn công tinh vi này, các giải pháp bảo mật truyền thống như tường lửa WAF hay hệ thống IDS dựa trên chữ ký tĩnh hoàn toàn không thể phát hiện.

Từ thực tế đó, việc nghiên cứu và ứng dụng các thuật toán **Học máy (Machine Learning)** để tự động học phân bố hành vi bình thường từ nhật ký truy cập (Request Logs), từ đó phát hiện các dị biệt hành vi trong chuỗi thời gian là một hướng tiếp cận khoa học, cấp thiết và có giá trị thực tiễn cao.

### 2. Mục tiêu nghiên cứu
- Nghiên cứu cơ sở lý thuyết về an toàn ứng dụng web, lỗ hổng BOLA/IDOR, kỹ thuật ghi nhật ký có cấu trúc và thuật toán học máy không giám sát Isolation Forest.

- Thiết kế bộ giả lập 4 kịch bản hành vi, thu thập 10.875 bản ghi log và xây dựng quy trình trích xuất vector 25 đặc trưng số theo cửa sổ trượt 5 phút.

### 1.1. Bối cảnh nghiên cứu và Lý do chọn đề tài
Trong quá trình chuyển đổi số, các hệ thống web lưu trữ và chia sẻ tài liệu trực tuyến (tương tự như Google Drive, OneDrive, Dropbox) đóng vai trò trung tâm trong hoạt động vận hành của các cơ quan, tổ chức giáo dục và doanh nghiệp. Người dùng thao tác liên tục trên hệ thống thông qua các giao thức web với hàng triệu HTTP Request mỗi ngày.

Bên cạnh các yêu cầu về tính sẵn sàng và tính năng tiện ích, an toàn thông tin trở thành điều kiện tiên quyết. Các cuộc tấn công mạng hiện đại đã chuyển dịch trọng tâm từ việc dò tìm lỗ hổng cú pháp sang khai thác **Lạm dụng Logic Nghiệp vụ (Business Logic Abuse)**. Những hành vi này diễn ra âm thầm, không gây lỗi hệ thống tức thì, khiến quản trị viên chỉ phát hiện sau khi dữ liệu đã bị rò rỉ hoặc phá hoại nghiêm trọng. Do đó, việc xây dựng một hệ thống có khả năng giám sát liên tục, phân tích hành vi theo thời gian và đưa ra cảnh báo tự động là yêu cầu cấp thiết.

### 1.2. Thách thức từ tấn công Business Logic Abuse và BOLA/IDOR
1. **Lạm dụng xuất dữ liệu hàng loạt (Export Abuse):** Người dùng gửi dồn dập 30 đến 50 yêu cầu xuất file CSV hoặc đóng gói ZIP trong 5 phút. Việc này gây nguy cơ thất thoát dữ liệu diện rộng và làm cạn kiệt tài nguyên CPU/RAM/Disk I/O của máy chủ.
2. **Xóa tài nguyên phá hoại (Delete Abuse):** Kẻ tấn công hoặc tài khoản bị chiếm đoạt (Account Takeover) gửi liên tiếp các yêu cầu xóa mềm hàng chục tệp tin trong nhiều thư mục khác nhau nhằm phá hoại dữ liệu.
3. **Dò quét phân quyền đối tượng (IDOR/BOLA Scan):** Kẻ tấn công thay đổi tuần tự các `file_id` trên URI để dò quét tệp tin riêng tư của người dùng khác, tạo ra chuỗi phản hồi lỗi 403 Forbidden và 404 Not Found tăng đột biến.

### 1.3. Hạn chế của các giải pháp phòng thủ truyền thống
- **Web Application Firewall (WAF) & IDS:** Hoạt động dựa trên việc đối khớp chữ ký (Signature Matching) hoặc phân tích cú pháp chuỗi ký tự trong Header/Body. Khi HTTP Request hoàn toàn hợp lệ về mặt cú pháp, WAF/IDS sẽ cho phép request đi qua.
- **Hệ thống luật cố định (Rule-based Thresholds):** Việc đặt ngưỡng cứng (ví dụ: giới hạn 20 request/phút) thường bộc lộ hai nhược điểm chí mạng: gây nhiều báo động giả (False Positives) đối với người dùng thao tác nhanh hợp lệ, hoặc bỏ sót các cuộc tấn công giãn cách thời gian (Low-and-Slow Attacks).

### 2.4. Thuật toán Isolation Forest và Cơ sở Toán học

#### 2.4.1. Nguyên lý cô lập (Isolation Principle)
Isolation Forest (Liu et al., 2008) hoạt động trên nguyên lý: Các điểm dữ liệu bất thường (outliers) có số lượng ít và giá trị đặc trưng khác biệt, do đó chúng bị cô lập rất nhanh (độ sâu cây $h(x)$ nhỏ) khi phân chia không gian ngẫu nhiên. Ngược lại, các điểm dữ liệu bình thường nằm trong vùng mật độ cao cần rất nhiều lần phân chia mới cô lập được.

```text
       Điểm Bình thường (Cần nhiều phép cắt)        Điểm Bất thường (Bị cô lập ngay)
                  │                                           │
         ┌────────┴────────┐                         ┌────────┴────────┐
         │                 │                         │     (Anomaly)   │ (Độ sâu h(x) nhỏ)
      ┌──┴──┐           ┌──┴──┐                      ▼                 ▼
      │     │           │     │                  [Cô lập sau 2-3 lần cắt ngẫu nhiên]
   [Dày đặc, h(x) lớn, cần nhiều cắt]
```

#### 2.4.2. Các công thức toán học cốt lõi

1. **Độ dài đường đi trung bình của cây tìm kiếm nhị phân $c(n)$:**
   $$c(n) = 2 \left( \ln(n - 1) + \gamma \right) - \frac{2(n - 1)}{n}$$
   Trong đó: $n$ là số lượng mẫu dữ liệu huấn luyện, và $\gamma \approx 0.5772156649$ là hằng số Euler-Mascheroni.

2. **Điểm bất thường chuẩn hóa (Anomaly Score) $s(x, n)$:**
   $$s(x, n) = 2^{-\frac{\mathbb{E}[h(x)]}{c(n)}}$$
   Trong đó $\mathbb{E}[h(x)] = \frac{1}{t} \sum_{i=1}^t h_i(x)$ là độ dài đường đi trung bình của mẫu $x$ trên toàn bộ $t$ cây cô lập iTree.
   - Khi $\mathbb{E}[h(x)] \to 0 \implies s(x, n) \to 1$: Mẫu $x$ chắc chắn là điểm bất thường.
   - Khi $\mathbb{E}[h(x)] \to c(n) \implies s(x, n) \to 0.5$: Mẫu $x$ không thể hiện tính dị biệt rõ ràng.
   - Khi $\mathbb{E}[h(x)] \to n - 1 \implies s(x, n) \to 0$: Mẫu $x$ hoàn toàn là điểm dữ liệu bình thường.

#### 2.4.3. So sánh với các thuật toán học máy khác

| Tiêu chí | Isolation Forest (Đề tài chọn) | One-Class SVM | Local Outlier Factor (LOF) | Autoencoder (Deep Learning) |
|---|---|---|---|---|
| **Độ phức tạp huấn luyện** | $O(t \cdot n \log \psi)$ — Tuyến tính, rất nhanh | $O(n^2)$ đến $O(n^3)$ — Chậm khi $n$ lớn | $O(n^2)$ — Tính khoảng cách $k$-NN | $O(n \cdot \text{epochs} \cdot \text{layers})$ — Rất nặng |
| **Bộ nhớ yêu cầu** | $O(t \cdot \psi)$ — Rất thấp | $O(n)$ — Lưu Support Vectors | $O(n)$ — Lưu toàn bộ dữ liệu | Lớn (tham số mạng nơ-ron) |
| **Tốc độ suy luận** | Dưới 1ms / window | Trung bình (vài ms) | Chậm (tra khoảng cách láng giềng) | Phụ thuộc GPU / Tensor Engine |
| **Tính giải thích** | Cao (dễ truy xuất Top Features) | Thấp (không gian Kernel Hilbert) | Trung bình (mật độ cục bộ) | Rất thấp (hộp đen) |

```text
│    [1] request_count: x₁ = N = |W| (Tổng số request trong cửa sổ 5 phút).              │
│    [2] unique_endpoint_count: x₂ = |⋃ {endpoint(rᵢ)}| (Số endpoint duy nhất).         │
│    [3] unique_method_count: x₃ = |⋃ {http_method(rᵢ)}| (Số method HTTP duy nhất).     │
│    [4] session_duration_sec: x₄ = max(t(rᵢ)) - min(t(rᵢ)) (Thời lượng phiên, giây).    │
│    [5] avg_inter_request_sec: x₅ = 1/(N-1) ∑ (t(rᵢ₊₁) - t(rᵢ)) (Khoảng cách TB giữa req).│
│    [6] min_inter_request_sec: x₆ = min (t(rᵢ₊₁) - t(rᵢ)) (Khoảng cách ngắn nhất - bot).│
│    [7] burst_rate: x₇ = N / max(x₄, 1.0) (Tốc độ bùng nổ request / giây).             │
│                                                                                        │
│ 2. Nhóm Lỗi & Phân quyền (Errors & Authorization):                                     │
│    [8] error_rate: x₈ = (1/N) ∑ 𝕀(status_code(rᵢ) ≥ 400) (Tỷ lệ lỗi HTTP tổng thể).    │
│    [9] forbidden_count: x₉ = ∑ 𝕀(status_code(rᵢ) = 403) (Số lần gặp lỗi 403 Forbidden).│
│    [10] forbidden_rate: x₁₀ = x₉ / N (Tỷ lệ lỗi 403 trên tổng request).                │
│    [11] not_found_count: x₁₁ = ∑ 𝕀(status_code(rᵢ) = 404) (Số lần gặp lỗi 404).        │
│    [12] not_found_rate: x₁₂ = x₁₁ / N (Tỷ lệ lỗi 404 trên tổng request).               │
│    [13] unique_failed_resource_id_count: x₁₃ = |⋃ {resource_id(rᵢ) | status ∈ {403,404}}|│
│                                                                                        │
│ 3. Nhóm Lạm dụng Nghiệp vụ (Business Logic Abuse):                                     │
│    [14] export_count: x₁₄ = ∑ 𝕀(action_type(rᵢ) = 'export') (Số lần xuất dữ liệu).     │
│    [15] export_ratio: x₁₅ = x₁₄ / N (Tỷ lệ thao tác xuất dữ liệu).                     │
│    [16] delete_count: x₁₆ = ∑ 𝕀(action_type(rᵢ) = 'delete') (Số lần xóa tài nguyên).   │
│    [17] delete_ratio: x₁₇ = x₁₆ / N (Tỷ lệ thao tác xóa tài nguyên).                   │
│    [18] unique_deleted_resource_count: x₁₈ = |⋃ {resource_id(rᵢ) | action = 'delete'}| │
│                                                                                        │
│ 4. Nhóm Dò quét Tài nguyên (Resource Exploration):                                     │
│    [19] unique_resource_id_count: x₁₉ = |⋃ {resource_id(rᵢ) ≠ NULL}| (Số ID tài nguyên).  │
│    [20] resource_id_request_ratio: x₂₀ = (1/N) ∑ 𝕀(resource_id(rᵢ) ≠ NULL).            │
│    [21] resource_id_change_rate: x₂₁ = 1/(N-1) ∑ 𝕀(resource_id(rᵢ₊₁) ≠ resource_id(rᵢ)).│
│                                                                                        │
│ 5. Nhóm Nhạy cảm & Hiệu năng Hệ thống (Sensitivity & Latency):                         │
│    [22] sensitive_request_count: x₂₂ = ∑ 𝕀(is_sensitive(rᵢ) = True).                   │
│    [23] sensitive_ratio: x₂₃ = x₂₂ / N (Tỷ lệ thao tác nhạy cảm).                       │
│    [24] max_sensitive_streak: x₂₄ = max streak of sensitive requests.                 │
│    [25] avg_response_time_ms: x₂₅ = (1/N) ∑ response_time_ms(rᵢ) (Thời gian phản hồi TB)│
└────────────────────────────────────────────────────────────────────────────────────────┘
```

- **Tập Train:** 8 cửa sổ (100% Normal) để mô hình học hành vi chuẩn.
- **Tập Validation:** 6 cửa sổ (3 Normal, 3 Anomaly: 1 Export Abuse, 1 Delete Abuse, 1 BOLA Scan) phục vụ tối ưu siêu tham số.
- **Tập Test:** 5 cửa sổ độc lập (2 Normal, 3 Anomaly: 1 Export Abuse, 1 Delete Abuse, 1 BOLA Scan) dùng để đánh giá khách quan.
